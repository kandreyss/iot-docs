\section{Облачный слой (Firebase Realtime Database)}

\subsection{Структура данных}

\begin{minted}{json}
{
  "current": { "t": 23.5, "h": 62.1, "g": 3200 },
  "history": {
    "1712700000": { "t": 22.1, "h": 64.2, "g": 2800 },
    "1712703600": { "t": 22.5, "h": 63.8, "g": 2900 }
  },
  "status": {
    "last_viewed": 1712703650
  }
}
\end{minted}

\subsection{Назначение веток в RTDB}

\begin{itemize}
    \item \texttt{/current} --- оперативное состояние для немедленного отображения в пользовательском интерфейсе.
    \item \texttt{/history/<hourEpoch>} --- архив телеметрических данных с часовым шагом.
    \item \texttt{/status/last\_viewed} --- технический маркер активности клиентского приложения.
\end{itemize}

В программном коде клиентского приложения реализован разбор как объекта, так и JSON-строки, что обеспечивает устойчивость системы к различным форматам полезной нагрузки в базе данных.

\subsection{Контракт данных}

\begin{itemize}
    \item \texttt{t}: температура, \texttt{number}, \textdegree C.
    \item \texttt{h}: влажность, \texttt{number}, \%.
    \item \texttt{g}: концентрация газа, \texttt{number} (сырой сигнал датчика; в клиентском приложении приводится к единицам \texttt{ppm} путём округления).
    \item Все временные метки --- \textbf{Unix epoch, секунды, UTC}.
\end{itemize}

\subsection{Преимущества выбранной модели хранения}

\begin{enumerate}
    \item \textbf{Разделение горячих и холодных данных:} ветка \texttt{/current} не перегружает историческое хранилище, а \texttt{/history} не оказывает влияния на скорость отображения актуальных данных.
    \item \textbf{Простота клиентской подписки:} для live-потока используется единственный наблюдаемый путь.
    \item \textbf{Предсказуемая ретроспектива:} исторические точки данных имеют фиксированную структуру ключей и допускают упорядочение по времени.
\end{enumerate}

\subsection{Архитектурный принцип клиентского приложения}

Клиентское приложение построено по схеме разделения логики доступа к данным (хуки) и визуального представления (компоненты). Данный подход снижает связанность программного кода: бизнес-логика доступа к RTDB не смешивается с логикой визуального представления.

\subsection{Поток актуальных данных (\texttt{useCurrentData})}

\begin{enumerate}
    \item Устанавливается подписка \texttt{onValue(ref(database, "current"))}.
    \item При каждом обновлении:
    \begin{itemize}
        \item полезная нагрузка обрабатывается функцией \texttt{parseTelemetryPayload};
        \item при успешном разборе обновляются состояния \texttt{data} и \texttt{last\allowbreak Updated};
        \item при возникновении ошибки обновляется состояние \texttt{error}.
    \end{itemize}
    \item Параллельно осуществляется отправка heartbeat-сигнала:
    \begin{itemize}
        \item непосредственно при монтировании компонента;
        \item затем с периодом \texttt{30 сек};
        \item в \texttt{/status/last\_viewed} записывается текущее UTC-время клиента.
    \end{itemize}
\end{enumerate}

Heartbeat-сигнал является управляющим воздействием для микропрограммного обеспечения, на основании которого определяется необходимость поддержания активного live-потока.

\subsection{Поток исторических данных (\texttt{useHistoryData})}

\begin{enumerate}
    \item По нажатию кнопки \texttt{Load data} компонентом применяется заданный диапазон дат.
    \item Хуком выполняется запрос \texttt{get(ref(database, "history"))}.
    \item На стороне клиента производится фильтрация записей по диапазону \texttt{startTimestamp\allowbreak..\allowbreak endTimestamp}.
    \item Каждая запись:
    \begin{itemize}
        \item проходит валидацию и разбор;
        \item преобразуется в объект типа \texttt{ChartDataPoint};
        \item сортируется по значению \texttt{timestamp}.
    \end{itemize}
    \item Компонент \texttt{HistoryCharts} строит график в выбранном режиме:
    \begin{itemize}
        \item все метрики;
        \item только температура;
        \item только влажность;
        \item только концентрация газа.
    \end{itemize}
\end{enumerate}

\subsection{Уровень пользовательского интерфейса}

\begin{itemize}
    \item \texttt{CurrentData}:
    \begin{itemize}
        \item 3 информационные карточки (temperature / humidity / gas);
        \item индикатор режима Live;
        \item время последнего обновления.
    \end{itemize}
    \item \texttt{HistoryCharts}:
    \begin{itemize}
        \item выбор диапазона дат;
        \item валидация диапазона;
        \item интерактивная визуализация на базе библиотеки Recharts.
    \end{itemize}
\end{itemize}

\subsection{Обработка ошибок и устойчивость интерфейса}

\begin{itemize}
    \item Ошибки чтения данных не приводят к неработоспособности приложения, а отображаются пользователю в виде контролируемого состояния.
    \item Некорректная полезная нагрузка отфильтровывается на этапе разбора и не нарушает работоспособность компонента.
    \item Отсутствие узла \texttt{/current} корректно интерпретируется как неактивное состояние потока, а не как критическая ошибка.
\end{itemize}

\subsection{Вывод по облачному и клиентскому уровням}

Совокупное применение Firebase и React-хуков обеспечивает реактивную модель отображения данных с чётким разделением ответственности: RTDB отвечает за хранение и синхронизацию состояния, хуки инкапсулируют логику доступа к данным, а компоненты сосредоточены на реализации пользовательского опыта и визуальной достоверности представления.
