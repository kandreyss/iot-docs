\section{Сквозные сценарии взаимодействия}

\subsection{Публикация текущих данных при активном пользователе}

\begin{minted}{text}
sequenceDiagram
  participant FE as Frontend
  participant FB as Firebase
  participant MCU as ESP8266

  FE->>FB: set /status/last_viewed = now (каждые 30с)
  MCU->>FB: get /status/last_viewed (каждые 10с)
  FB-->>MCU: last_viewed
  MCU->>MCU: diff = |epoch - last_viewed|
  alt diff < 120s
    MCU->>FB: set /current = {t,h,g}
    FB-->>FE: onValue(/current) update
  else diff >= 120s
    MCU->>FB: remove /current
    FB-->>FE: /current = null
  end
\end{minted}

\subsubsection*{Описание сценария}

Данный сценарий реализует механизм адаптивной передачи данных. При наличии недавней активности пользователя в интерфейсе системой поддерживается активный live-поток. При отсутствии активности поток отключается автоматически, что сокращает количество операций записи и чтения, а также снижает потребление сетевых ресурсов.

\subsection{Почасовая запись истории}

\begin{minted}{text}
sequenceDiagram
  participant MCU as ESP8266
  participant FB as Firebase
  participant FE as Frontend

  MCU->>MCU: Каждый цикл проверка epoch % 3600 < 60
  MCU->>FB: set /history/{hourStartEpoch} = {t,h,g}
  FE->>FB: get /history (по кнопке Load data)
  FE->>FE: фильтрация по диапазону и сортировка
  FE->>FE: рендер графиков
\end{minted}

\subsubsection*{Описание сценария}

Исторический поток данных отделён от live-потока и функционирует с меньшей частотой. Данное решение предотвращает накопление избыточных записей в базе данных и сохраняет достаточную аналитическую ценность для построения графиков и формирования отчётности.

\section{Машина состояний микропрограммного обеспечения (упрощённо)}

\begin{minted}{text}
stateDiagram-v2
  [*] --> Boot
  Boot --> DisplayInit
  DisplayInit --> WifiTry
  WifiTry --> WifiOk: connected
  WifiTry --> Offline: timeout
  WifiOk --> FirebaseInit
  FirebaseInit --> SensorInit
  Offline --> SensorInit
  SensorInit --> Monitoring
  Monitoring --> Monitoring: read sensors + render OLED
  Monitoring --> CloudSync: Wi-Fi && FirebaseReady && validTime
  CloudSync --> Monitoring
\end{minted}

\subsection{Пояснение состояний}

\begin{itemize}
    \item \textbf{Boot / DisplayInit} --- аппаратная готовность и первичная верификация канала локальной индикации.
    \item \textbf{WifiTry / WifiOk / Offline} --- ветвление по результату проверки сетевой доступности без блокировки основной функции устройства.
    \item \textbf{FirebaseInit} --- подготовка облачного канала при условии наличия сетевого соединения.
    \item \textbf{SensorInit / Monitoring} --- переход в целевой рабочий режим наблюдения.
    \item \textbf{CloudSync} --- условный контур облачного обмена, активируемый исключительно при выполнении всех необходимых предусловий.
\end{itemize}

\section{Ключевые технические особенности реализации}

\begin{enumerate}
    \item \textbf{UTC как единая временная шкала}: NTP offset = \texttt{0}, временные метки хранятся в формате epoch-секунд.
    \item \textbf{Асинхронный Firebase-контур}: сетевые операции не блокируют цикл измерений и вывода данных на индикатор.
    \item \textbf{Событийное управление live-потоком}: существование узла \texttt{/current} обусловлено наличием heartbeat-сигнала от клиентского приложения.
    \item \textbf{Экономичный исторический контур}: архив формируется батчево и запрашивается по требованию.
    \item \textbf{Явный fail-fast на уровне OLED}: в текущей конфигурации отсутствие дисплея классифицируется как критический отказ.
\end{enumerate}

\section{Ограничения текущей реализации}

\begin{enumerate}
    \item \textbf{Хранение секретов в \texttt{secrets.h}}: учётные данные размещены непосредственно в исходном коде, что требует усиления политики безопасности.
    \item \textbf{Чтение всей ветки истории}: при росте объёма накопленных данных возрастает нагрузка на сеть и на клиентскую фильтрацию.
    \item \textbf{Отсутствие аутентификации устройства}: использование модели \texttt{NoAuth} снижает уровень защищённости подключения устройства.
    \item \textbf{Жёсткая реакция на сбой OLED}: деградированный режим работы без дисплея не реализован.
\end{enumerate}

\section{Рекомендации по дальнейшему развитию}

\begin{enumerate}
    \item Вынести учётные данные в приватную конфигурацию и исключить из репозитория.
    \item Внедрить аутентификацию устройства посредством custom token через доверенный backend.
    \item Перейти к диапазонным запросам истории с индексированием по времени.
    \item Реализовать буферизацию измерений в режиме оффлайн с последующей передачей после восстановления сетевого соединения.
    \item Добавить телеметрию состояния устройства: uptime, RSSI, ошибки публикации, статистику повторных попыток.
\end{enumerate}

\section{Итоговое заключение}

Разработанная система представляет собой завершённый технический контур IoT-мониторинга: микроконтроллерный модуль обеспечивает стабильный сбор телеметрии, облачный слой выполняет согласованное хранение и синхронизацию данных, а клиентское приложение предоставляет пользователю актуальную и историческую картину состояния контролируемой среды.

Ключевым достоинством принятой архитектуры является предсказуемость поведения системы под нагрузкой, достигаемая за счёт разделения потоков данных, асинхронного обмена и строгой временной модели на основе UTC epoch.
