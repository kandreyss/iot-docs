\section{Назначение системы}

В рамках проекта реализован полный IoT-контур для мониторинга параметров окружающей среды в режиме реального времени. Система предназначена для непрерывного сбора телеметрии, визуализации текущих значений, накопления исторических данных и обеспечения удалённого контроля состояния объекта наблюдения.

С технической точки зрения разработанное решение обеспечивает решение четырёх ключевых задач:

\begin{enumerate}
    \item \textbf{Сбор и первичная обработка телеметрии.} Микроконтроллером (ESP8266 / NodeMCU v2) осуществляется считывание показаний датчиков температуры, влажности и концентрации газа, первичная фильтрация данных и их отображение на OLED-дисплее.
    \item \textbf{Frontend (React + TypeScript)} выполняет чтение данных из Firebase:
    \begin{itemize}
        \item \texttt{current} --- актуальные показания в режиме реального времени;
        \item \texttt{history} --- почасовая история измерений.
    \end{itemize}
    \item \textbf{Оптимизация трафика и нагрузки.} Клиентским приложением производится отправка heartbeat-сигнала (\texttt{/status/last\_viewed}), на основании которого микропрограммным обеспечением определяется факт активности пользователя и принимается решение о публикации ветки \texttt{current}.
    \item \textbf{Формирование аналитической базы.} Микропрограммным обеспечением выполняется сохранение агрегированной истории в Firebase по часовым срезам, что обеспечивает возможность построения графиков, анализа трендов и оценки динамики параметров без непрерывной потоковой передачи данных.
\end{enumerate}

\subsection{Функциональные границы решения}

В текущей реализации система ориентирована на решение задач телеметрии и визуализации без подсистемы управления исполнительными устройствами. Данное архитектурное решение принято намеренно: контур «измерение → хранение → отображение» изолирован от контура «управление → обратная связь», что снижает риск возникновения ошибок и упрощает сопровождение системы.

\begin{itemize}
    \item \textbf{Входит в область решения:} сбор метрик, публикация актуальных данных, хранение истории, интерактивный просмотр в веб-интерфейсе.
    \item \textbf{Не входит в область решения:} аварийные команды на оборудование, разграничение ролей доступа пользователей, локальное долговременное хранилище на устройстве.
\end{itemize}

\subsection{Критерии качества системы}

Система оценивается по следующим базовым критериям:

\begin{itemize}
    \item \textbf{Надёжность сбора данных:} цикл измерений выполняется периодически и не блокируется сетевыми операциями.
    \item \textbf{Согласованность времени:} все временные метки приводятся к UTC epoch, что исключает ошибки при интерпретации данных на различных клиентах.
    \item \textbf{Читаемость интерфейса:} пользователю предоставляется как текущее состояние, так и исторический контекст в структурированном формате.
    \item \textbf{Масштабируемость по данным:} архитектура разделяет «live»-ветку и историческую ветку, снижая нагрузку при росте объёма измерений.
\end{itemize}

\section{Состав репозитория}

\subsection{Логическая декомпозиция проекта}

\begin{itemize}
    \item \texttt{course\_work/} --- микропрограммное обеспечение микроконтроллера (PlatformIO, Arduino framework). Данный модуль включает аппаратную инициализацию, циклический сбор данных, синхронизацию времени и обмен данными с Firebase.
    \item \texttt{iot-dashboard/} --- веб-панель мониторинга (Vite + React + TypeScript + MUI + Recharts + Firebase SDK). Модуль обеспечивает отображение текущих и исторических данных, пользовательскую фильтрацию и формирование heartbeat-сигналов активности.
    \item \texttt{generate/} --- вспомогательные скрипты генерации данных, не задействованные в основном runtime-контуре взаимодействия микропрограммного обеспечения и клиентского приложения. Применяются для подготовки тестовых и демонстрационных наборов данных, а также отладки визуализаций.
\end{itemize}

\subsection{Принцип разделения ответственности}

Декомпозиция по директориям выполнена в соответствии с принципом единственной ответственности: код микроконтроллера не содержит логики пользовательского интерфейса, а клиентское приложение не содержит аппаратно-зависимых алгоритмов. Данный подход позволяет осуществлять независимую разработку обеих частей системы и упрощает проведение тестирования.

\section{Архитектура на уровне подсистем}

На приведённой диаграмме отображён полный маршрут телеметрии: от физического измерения до отображения данных на клиенте. Центральная роль отведена Firebase RTDB как точке синхронизации между асинхронным микропрограммным обеспечением и реактивным веб-интерфейсом.

\begin{itemize}
    \item Подсистема ESP8266 формирует данные и инициирует их запись.
    \item Firebase обеспечивает хранение состояния и обработку подписок и запросов на чтение.
    \item Клиентское приложение интерпретирует данные, отображает их и формирует heartbeat-сигнал для управления жизненным циклом ветки \texttt{/current}.
\end{itemize}

\subsection{Поток данных и управляющий поток}

В архитектуре системы одновременно функционируют два взаимосвязанных потока:

\begin{enumerate}
    \item \textbf{Поток измерений:} датчики → микропрограммное обеспечение → Firebase → клиентское приложение.
    \item \textbf{Сигнал активности пользователя:} клиентское приложение → Firebase (\texttt{/status/\allowbreak last\_viewed}) → микропрограммное обеспечение.
\end{enumerate}

Данный подход обеспечивает баланс между актуальностью данных и экономией ресурсов: «живая» ветка публикуется исключительно в периоды подтверждённой пользовательской активности.
